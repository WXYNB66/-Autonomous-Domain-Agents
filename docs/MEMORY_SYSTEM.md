# 记忆与版本系统

## 1. 业务记忆使用自然语言，技术一致性使用版本

角色不依赖跨角色私有 `profile / plan / risk_output` 字段理解业务。它们读取的工作记忆由以下可读材料构成：

- 用户最新原话、明确更正与时间顺序；
- 已批准的角色专业报告与协作 Brief；
- 带来源、时点、限制的 Research / 工具 Evidence Envelope；
- 尚未解决的冲突、假设和最小追问；
- 技术连续性事件（只说明本轮未完成，不携带业务结论）。

版本协调器负责技术事实：哪一份会谈快照已提交、浏览器应显示什么、当前等待合同和角色租约属于哪个版本。

## 2. 更正优先

金额、期限、用途、可动用性、收入稳定性和目标优先级的最新明确表达，会使依赖旧前提的结论进入“需重新审查”状态。不是删除旧历史，而是明确：旧结论不能继续作为当前方案前提。

角色必须把更正转化为业务影响，例如：取消首付目标后，哪些资金桶和现金流假设失效；教育金提前后，哪些长期配置不能沿用。

## 3. 工作记忆不是聊天全文

工作记忆应优先保留决定当前行动的信息，而不是压缩成无来源的摘要。压缩时优先删除已解决过程、重复寒暄和被新更正覆盖的细节；不得删除最新更正、关键金额/期限、证据限制、待决冲突和角色已交付成果。

Eleanor 的工作集还可附带授权工具能力摘要，但能力摘要不是事实、不是用户授权，也不是工具结果。

## 4. 版本提交原则

只有完整回合才生成新的 `meeting_version`。一个版本同时包含报告视图、等待合同、当前角色、运行状态和审计引用。前端不得混合不同版本的这些部分。

这解决“后端有三个不同进度”的问题：浏览器、Redis 和数据库不各自判断谁最新，而由版本协调器提交一个权威快照。

## 5. 恢复与长期咨询

用户离线、WebSocket 重连、角色超时或工具失败后，会话保留。恢复时从最新已提交版本与自然语言工作记忆继续，不重新播放旧角色、不用失败 fallback 取代已交付成果。

# 评估框架：以职业能力而非流程通过率为核心

## 1. 为什么不能只看测试通过率

多智能体系统很容易出现“测试断言通过，但用户没有得到价值”的情况：角色重复发言、过度追问、工具被调用却没有改变结论、合理报告被质量门吞掉，或所有人都在说正确但无用的话。

因此，评估必须同时观察角色对话、内部事件链、工具证据和最终业务成果。

## 2. 四维评分

| 维度 | 审查问题 |
|---|---|
| 用户价值 | 是否回答真正问题？是否减少绕路与无效追问？是否给出可推进的下一步？ |
| 专业能力 | 是否有岗位独有判断？是否越权、空泛或被其他角色替代？ |
| 证据质量 | 是否区分用户事实、角色判断、外部证据、假设与限制？ |
| 系统可靠性 | 是否正确处理更正、冲突、重复、失败、延迟、断线与停止？ |

## 3. 必测场景

- 高噪声用户表达；
- 用户在长对话中更正金额、期限、用途或可动用性；
- 角色报告之间出现冲突；
- 应当条件化推进而非追问的场景；
- 应当请求用户、数据分析师或其他专家的场景；
- 工具应授权、应拒绝、编译失败、运行失败和返回不改变结论的场景；
- 数据证据晚到、重复请求、断线恢复和事件回放；
- 暂无新增动作但应保留会谈继续权的场景。

## 4. 质量门的正确位置

质量门应当硬拦截：编造事实、伪造工具输出、明确关键事实冲突、越权承诺和安全边界破坏。

质量门不应因为报告是条件性的、表达不够漂亮或流程没有跑完整，就替换掉已完成的合理业务成果。对于可修复问题，应优先局部修复与来源级诊断。

## 5. 真实 LLM 验收

真实模型验收应记录：

- 场景与用户画像；
- 每轮用户/角色自然语言内容；
- 编排决定与理由；
- 工具意图、授权、证据和失败语义；
- 延迟、模型失败与重试；
- 审查者对业务成果的逐轮评分。

最终结论不应是“30/30 通过”，而应解释：哪些能力稳定、哪些问题属于系统设计、哪些问题属于外部模型尾延迟，以及是否达到面向用户交付的标准。

## 6. 以原文与链路审查替代二元通过率

每次复杂验收至少保留：用户原话、角色原话、最新会谈版本、角色租约/恢复事件、工具候选与授权结果、工具证据、质量审计结论和最终交付文本。评价者先完整阅读一个用户的连续会谈，再判断专业成果是否对该用户真正有价值。

`tool_calls > 0` 不代表工具成功，`quality_gate_passed` 也不代表用户体验合格。应分别判断：工具是否改变行动、授权拒绝是否被正确解释、技术失败是否保留阶段成果、人格化交付是否无损保留专业判断，以及编排层是否错误地终止或抢占角色会谈。

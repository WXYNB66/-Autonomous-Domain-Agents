# 评估标准：审查业务成果，也审查系统是否妨碍角色发挥

## 1. 评分对象

评估不是“JSON 合不合法”或“工具有没有被调用”。审查者必须同时阅读：用户原话、角色最终回复、专业正文、工作记忆影响、工具审计、版本/恢复事件。

| 维度 | 核心问题 |
|---|---|
| 用户价值 | 是否理解真正诉求、先给阶段成果、避免表单化追问？ |
| 岗位专业性 | 是否给出角色独有判断、避免越权和伪确定？ |
| 事实与证据 | 是否区分用户事实、条件假设、工具事实与外部证据？ |
| 工具价值 | 是否该用才用；工具不同结果是否改变行动；失败后是否不编造？ |
| 会谈连续性 | 是否吸收更正、保留版本、等待可恢复、失败不关会？ |
| 交付体验 | 专业正文是否完整进入自然表达，语气是否符合角色和用户状态？ |

## 2. 强制测试矩阵

- 逐句真实用户：简短开场、情绪、噪声、跑题、专业挑战、表达不清；
- 最新更正覆盖旧金额、期限、用途、优先级；
- 不完整信息下先产生价值；
- 角色委托、编排尊重/不执行委托、角色租约续用；
- 应调用工具、应不调用工具、币种/来源缺失、授权拒绝、Manifest 不就绪、编译失败、网关失败、Evidence 返回；
- 安全门反馈、人格化无损、技术维护提示仅在无安全成果时；
- 双实例、晚到事件、断线重连、版本竞争和角色技术失败恢复。

## 3. 报告纪律

每一个“问题”都必须附原文：用户原话、角色原话、相关审计字段和人工判断。不要仅凭状态码说角色不好；也不要因为状态码通过就说用户体验好。

工具 `tool_calls=1` 不等于成功；必须同时检查网关状态为 `succeeded`、Evidence Brief 非空、角色明确说明证据如何改变方案。

## 4. 通过标准

一个角色只有同时满足以下条件才可称工具闭环通过：

1. 在真实会谈中被正确路由或可解释地直接验收；
2. 主成果在信息不完整时仍对用户有价值；
3. 最新更正影响后续推理；
4. 最终交付不丢失专业正文；
5. 在至少一个自然语义场景中成功完成工具的选择、授权、Manifest、编译、网关、Evidence 解读；
6. 工具和技术失败不导致编造、业务 fallback 或整场关闭。

评分应给出“可上线、可内测、有条件通过、未通过”的业务结论及原因，而非只给通过率。

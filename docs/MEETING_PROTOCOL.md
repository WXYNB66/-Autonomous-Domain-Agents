# 动态会谈协议：角色租约、阶段成果与恢复

## 1. 新事件不是重新开会的命令

用户每一句补充、纠正、闲聊、工具证据或角色报告都会形成事件。运行时先提交版本并构造工作记忆，再判断是否续用当前角色租约或选择新角色。

```text
用户回复当前角色的关键问题
→ 默认续用当前角色
→ 由该角色吸收新事实并推进自己的目标

用户带来改变角色归属的新问题 / 旧前提失效 / 角色委托
→ 编排器做有限语义路由
```

这避免每个用户句子都由编排器重新裁决，造成角色被抢走、延迟叠加和重复追问。

## 2. 角色回合的合法结果

每个角色回合必须属于以下之一：

| 结果 | 用户获得什么 | 会谈状态 |
|---|---|---|
| 阶段性成果 | 已确认事实、条件边界、可逆行动 | 可继续或等待 |
| 最小追问 | 已先交付价值，只缺一个真正改变下一步的事实 | 等待该角色租约 |
| 协作 Brief | 本角色成果 + 另一个岗位可带来的不可替代价值 | 编排器评估委托 |
| 工具观察后成果 | Evidence Brief 如何改变方案 | 可继续或等待 |
| 无新增贡献 | 明确说明已有结论仍可沿用 | 当前回合停止 |
| 技术连续性 | 不把未完成工作当结论，保留会谈 | 恢复、等待或换角色 |

不存在“角色本轮技术失败，所以整场会议 failed_closed”的合法业务语义。

## 3. 编排器权限

编排器可以：路由、续用/释放租约、维护版本、处理技术恢复、避免无新增价值的重复发言。

编排器不可以：替角色确定专业方案、否决角色已经完成的岗位成果、因为另一个角色还没发言而强制插入、把用户的长期会谈关闭。

角色委托默认被尊重；若暂不执行，编排器记录非业务裁决式理由，原角色仍对当前条件性成果负责。

## 4. 等待不是结束

`waiting_contract` 记录：当前等待的最小事实、提出问题的角色、已交付的阶段价值和为什么其他角色当前无法新增价值。用户可以数天后继续；新消息必须用版本与自然语言工作记忆恢复，而不是丢失或把旧等待文本当结论。

## 5. 恢复协议

角色或工具技术失败时：

1. 持久化已经提交的版本；
2. 写入技术连续性事件；
3. 不将失败文本作为用户事实或角色报告；
4. 编排器只依据用户原话、已批准报告、Research Brief 和工具证据继续判断；
5. 若没有安全成果，才发送不含业务建议的维护提示。

## 6. 前端协议

前端消费完整、已提交的 `meeting_version` 快照。报告、等待合同、当前角色和会谈状态必须来自同一版本。晚到事件、双 WebSocket、Redis/数据库不同步都不得覆盖较新的已提交版本。
